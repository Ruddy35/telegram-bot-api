# Потребление памяти и «горячий» рестарт TDLib-инстансов

Документ описывает, почему Bot API сервер со временем занимает всё больше ОЗУ, и как этот форк
освобождает память **без перезапуска процесса и без ошибок для ботов**.

Версии: Bot API 10.3, TDLib 1.8.67 (сабмодуль `td`, коммит `bc9c263`). Ссылки на код ниже даны
для этих версий.

## Коротко

* Рост памяти — не утечка в классическом смысле: TDLib намеренно держит в памяти **все** объекты,
  которые бот когда-либо видел (файлы, пользователи, чаты, диалоги). Освобождаются они только
  вместе со всем TDLib-инстансом. Поэтому помогает рестарт.
* Каждый бот на сервере работает в своём TDLib-инстансе. Форк умеет **закрыть и заново открыть
  инстанс одного бота на лету**: сначала новые запросы бота откладываются, текущие дорабатывают,
  все полученные апдейты дообрабатываются, затем инстанс закрывается и открывается из той же
  базы. Отложенные запросы выполняются новым инстансом.
* Для бота это выглядит как задержка ответов на ~0,5–1 с (плюс время завершения его текущих
  запросов). Запросы не падают, апдейты не теряются и не дублируются, вебхук и `allowed_updates`
  сохраняются, повторного логина нет. Остальные боты процесса не затрагиваются.
* Рестарт запускается по объёму RSS процесса, по времени работы инстанса или вручную через порт
  статистики.

## Почему растёт память

Профиль из продакшена (Bot API 9.2/TDLight, TDLib 1.8.52) показал основные точки аллокаций:
`register_photo_size()` → `FileManager::register_remote()` (~47–50 % выборки), создание сообщений
в `MessagesManager` (~22–24 %), метаданные видео и документов, кэш сообщений самого Bot API.
Разбор по исходникам:

| Что | Где | Освобождается? |
|---|---|---|
| Узлы файлов и индексы: `file_nodes_`, `file_id_info_`, `remote_location_to_file_id_` | `td/td/telegram/files/FileManager.h:892-898`, `FileManager::register_remote` в `FileManager.cpp:1747` | **Нет.** Для каждого нового удалённого файла (каждый размер фото, превью, видео, документ) создаётся `FileNode` + `FileIdInfo`. Сборщика мусора нет: целочисленный `file_id` по контракту TDLib API действителен всё время жизни инстанса. |
| Метаданные медиа: `VideosManager::videos_`, `DocumentsManager::documents_`, аналогично аудио, анимации, стикеры | `VideosManager.h:117`, `DocumentsManager.h:144` | **Нет**, ключом служит `FileId`. |
| Диалоги `MessagesManager::dialogs_` | `MessagesManager.h:3354` | **Нет**, объект `Dialog` создаётся на каждый чат и живёт до конца инстанса. |
| Пользователи и чаты `UserManager::users_`, `ChatManager::chats_/channels_` | `UserManager.h:1256`, `ChatManager.h:952-958` | **Нет.** |
| Сообщения `Dialog::messages` | `MessagesManager.cpp:8893-8985` (`unload_dialog`), `13197` (`can_unload_message`) | **Да**, через `message_unload_delay` (для ботов по умолчанию 1800 с). Объём ограничен «поток сообщений × 30 минут» — это не утечка. |
| Кэш Bot API `Client::messages_` | `telegram-bot-api/Client.cpp`, обработка `updateDeleteMessages` | **Да**, синхронно с TDLib (`from_cache = true`). |
| Кэш Bot API `users_`, `chats_`, `groups_`, `supergroups_` | `telegram-bot-api/Client.h` | **Нет**, растёт вместе с TDLib. |

Итог: память инстанса растёт пропорционально числу **уникальных** пользователей, чатов и файлов,
которые бот увидел с момента старта. У крупного бота, который принимает и отправляет много медиа,
за сутки набегают гигабайты. Точечно освобождать эти структуры нельзя: на них ссылаются десятки
менеджеров TDLib, а `file_id` должны оставаться валидными. Единственный корректный способ вернуть
память — уничтожить инстанс. Это и делает рестарт процесса, только с простоем для всех ботов сразу.

## Как устроен рестарт инстанса

Состояния в `ClientManager` (на бота): `None → Draining → Closing → None`.
Состояния в `Client`: `None → Draining → GoingOffline → Offline → Closing`.

1. `ClientManager` перестаёт передавать запросы бота в `Client` и складывает их в очередь
   (`ClientInfo::restart_queries_`, до 10 000 штук; сверх этого — `429 retry_after 1`).
2. `Client::restart()`:
   * сразу отвечает на висящий long polling `getUpdates` (тем, что есть в очереди апдейтов;
     следующий `getUpdates` бота попадёт в очередь из п. 1 и выполнится новым инстансом);
   * ставит вебхук на паузу: `WebhookActor` перестаёт отправлять новые апдейты и ждёт ответа на уже
     отправленные. Поэтому после рестарта ни один апдейт не будет отправлен повторно;
   * ждёт, пока не останется активных запросов бота, незавершённых запросов к TDLib и
     частично обработанных апдейтов (очереди `new_message_queues_` и т. п.).
3. `setNetworkType(networkTypeNone)`: TDLib перестаёт получать новые апдейты с сервера. Через
   0,5 с условие из п. 2 проверяется ещё раз. Если за это время пришёл апдейт, которому нужна сеть
   (например, загрузка сообщения, на которое ответили), сеть включается обратно и шаг повторяется.
   Так гарантируется, что TDLib не закроется посреди обработки апдейта. Апдейты, которые сервер
   Telegram ещё не отдал, инстанс заберёт после открытия через `getDifference`: `pts`/`qts`
   сохраняются при закрытии.
4. `td_api::close`: TDLib сбрасывает состояние на диск и освобождает всю память инстанса.
5. Когда `Client` остановился, `ClientManager` создаёт новый `Client` с тем же токеном и той же
   директорией. Ключ авторизации лежит в `td.binlog`, поэтому повторного логина нет. Вебхук
   восстанавливается из `webhooks_db.binlog` так же, как при старте сервера. После этого новому
   клиенту передаются отложенные запросы, и он выполняет их, как только TDLib будет готов.
6. На glibc через 10 с вызывается `malloc_trim(0)`, чтобы вернуть освобождённую память ОС.

Если за `--tdlib-restart-drain-timeout` секунд бот так и не «затих» (например, идёт долгая
загрузка большого файла), рестарт **отменяется**: вебхук и сеть возвращаются, отложенные запросы
уходят в старый инстанс, и бот работает дальше как обычно. Следующая автоматическая попытка
будет через 5 минут (с каждой неудачей пауза растёт, максимум 1 час). Одновременно
перезапускается не больше одного бота, между автоматическими рестартами выдерживается
`--tdlib-restart-cooldown`.

Если инстанс начал закрываться по другой причине (`logOut`, `close`, отзыв токена, остановка
сервера), рестарт отменяется, и дальше всё работает как в upstream.

## Параметры запуска

| Параметр | По умолчанию | Описание |
|---|---|---|
| `--tdlib-restart-memory-limit=<МБ>` | выкл. | Пока RSS процесса выше лимита, по одному перезапускать инстансы самых активных ботов. Активность оценивается по числу апдейтов TDLib с момента старта инстанса. |
| `--tdlib-restart-min-uptime=<с>` | 3600 | Минимальное время работы инстанса, после которого его можно перезапустить из-за лимита памяти. Защищает от постоянных перезапусков, если RSS не падает, например из-за фрагментации кучи. |
| `--tdlib-restart-interval=<с>` | выкл. | Перезапускать инстанс каждого бота после указанного времени работы (+0–10 % случайной задержки, чтобы рестарты не совпадали по времени). |
| `--tdlib-restart-drain-timeout=<с>` | 30 | Сколько ждать завершения текущих запросов бота перед рестартом. Это же максимальная задержка запросов на время рестарта. |
| `--tdlib-restart-cooldown=<с>` | 10 | Минимальная пауза между автоматическими рестартами (любых ботов). |
| `--message-unload-delay=<с>` | значение TDLib (1800) | Через сколько секунд неиспользуемые сообщения выгружаются из памяти TDLib. Допустимо 60–86400. Меньшее значение уменьшает память под сообщения, но увеличивает число запросов к серверу Telegram за старыми сообщениями (ответы, callback-кнопки и т. п.). |

Без этих параметров сервер работает так же, как upstream: при старте инстанса добавляется только
сброс опции `message_unload_delay` к значению по умолчанию.

Пример для сервера с ~36 ботами в контейнере с лимитом 8 ГБ:

```
telegram-bot-api ... \
  --tdlib-restart-memory-limit=5500 \
  --tdlib-restart-min-uptime=3600 \
  --tdlib-restart-interval=43200
```

## Ручной запуск и мониторинг

Через порт статистики (`--http-stat-port`):

```
curl 'http://127.0.0.1:<stat-port>/?restart=<bot_id>'   # перезапустить инстанс одного бота
curl 'http://127.0.0.1:<stat-port>/?restart=all'        # перезапустить все по очереди
```

`<bot_id>` — числовая часть токена до двоеточия. Ответ содержит `tdlib_restart_requested <N>`.
Порт статистики должен быть доступен только из внутренней сети. Это уже так для upstream:
через него, например, меняется уровень логирования.

Новые строки в выводе статистики:

* общие: `tdlib_restart_count`, `tdlib_failed_restart_count`;
* по боту: `tdlib_update_count` (апдейтов с момента старта инстанса), `tdlib_restart_count`,
  `tdlib_next_restart_in`, а во время рестарта ещё `tdlib_restart_state`,
  `tdlib_restart_duration`, `tdlib_restart_delayed_query_count`.

`uptime` бота теперь показывает время работы текущего инстанса.

В логе (уровень WARNING):

```
Start graceful restart of TDLib instance of bot <id> with uptime <s> because of <request|memory limit|uptime>
Close TDLib instance for restart
Closed TDLib instance of bot <id> for restart in <s> seconds; have <N> delayed queries
Failed to restart TDLib instance of bot <id>: <reason>
Released free memory to the OS in <s> seconds
```

## Тестирование

`test/restart/restart_test.py` — офлайн-интеграционный тест, сеть Telegram для него не нужна.
Тестовый бот помечается в `td.binlog` как авторизованный (`restart-test-fake-auth`), в очередь
апдейтов заранее кладутся события (`restart-test-fake-updates`). Тест запускает настоящий сервер и
проверяет:

* **webhook**: 3 рестарта во время доставки 300 апдейтов на локальный вебхук (10 соединений, ответ
  через 0,3 с) при параллельной нагрузке запросами. Каждый апдейт доставлен ровно один раз;
  ~25 000 запросов, 0 ошибок, максимальная задержка 0,83 с;
* **polling**: висящий `getUpdates` отвечает сразу, дальнейший polling продолжается, апдейты не
  теряются;
* **drain_timeout**: запрос, который не может завершиться, откладывает рестарт; через таймаут
  рестарт отменяется, запросы обслуживаются с задержкой не больше таймаута, ошибок нет;
* **policy**: рестарты по лимиту памяти (11 рестартов подряд, RSS стабилен, утечек в самом
  механизме нет) и по времени работы.

```
cmake --build build --target telegram-bot-api restart-test-fake-auth restart-test-fake-updates
python3 test/restart/restart_test.py build
```

Офлайн-тест не воспроизводит реальную нагрузку Telegram: апдейты из сети, загрузку и отправку
файлов, `getDifference` после переоткрытия. Перед продом нужен прогон на стенде с реальными
(тестовыми) ботами, см. ниже.

## План выката

1. Собрать образ из этого форка. Сейчас в проде TDLight Bot API 9.2. Этот форк основан на
   официальном `tdlib/telegram-bot-api` 10.3, поэтому сначала проверить, что второй сервис не
   использует методы и параметры, которые есть только в TDLight.
2. Стенд: несколько тестовых ботов с вебхуком и с polling, нагрузка близкая к реальной. Вызывать
   `?restart=<bot_id>` в цикле и следить за ошибками у ботов, дублями `update_id`, «потерянными»
   апдейтами и строками `Failed to restart` в логе.
3. Прод, этап 1: только ручные рестарты самого «тяжёлого» бота в спокойное время. Смотреть RSS до
   и после и `tdlib_restart_count`.
4. Прод, этап 2: включить `--tdlib-restart-memory-limit` с запасом относительно лимита контейнера.
   Позже при желании добавить `--tdlib-restart-interval`.

## Ограничения

* Пока у бота идёт долгий запрос (загрузка большого файла, долгий `sendMediaGroup`), рестарт
  откладывается. Его запросы на время ожидания задерживаются, максимум на
  `--tdlib-restart-drain-timeout`.
* На glibc RSS после рестарта может опускаться не сразу и не полностью из-за фрагментации кучи,
  но освобождённая память переиспользуется следующими аллокациями. `malloc_trim` помогает вернуть
  её ОС. musl, jemalloc и mimalloc возвращают память активнее.
* На время рестарта бот не получает новые апдейты (около секунды). Они не теряются: приходят
  после переоткрытия инстанса.
* В upstream есть редкое падение на `CHECK` в `ObjectPool` при остановке процесса (SIGTERM) под
  нагрузкой. Воспроизводится и без этих изменений, на работу рестарта инстансов не влияет.
